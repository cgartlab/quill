# 反驳（找反例反驳草稿）

> 本文件在**第八步**加载——草稿写完后，由模型找反例与反论来反驳自己的草稿。这是规则，不是可选步骤，也不靠定期更新。

## 找什么

针对核心论点与每条支撑要点，主动找：有没有反例？有没有更合理的反论？证据是否站得住？

**反例五类**：

- **事实反例**：证据错了 / 过时 / 二手当一手。
- **逻辑反例**：推理链有漏洞（归纳样本偏倚 / 演绎大前提不成立 / 类比失当）。
- **范围反例**：论点过宽，存在明显不适用场景。
- **价值反例**：有更重要视角被忽略。
- **困惑反例**：**一个善意的读者在这里跟不上了**——哪一句需要多补半句？读者卡住的位置往往正是论证的薄弱处。

## 两条纪律

- **锚定原文**：每条反例必须写清位置 + 引用草稿里的一句话。**指不出位置的挑战直接丢掉**，不要软化后保留。
- **不制造批评凑数**：某一类确实没问题就写「未发现实质问题」，不要为了填满五类硬挑。开口先给最强的一条，不做三明治式铺垫。

## 两阶段，不许边找边改

- **诊断阶段**：一次找全，只出反例清单，**不改稿、不重写**。
- **处理阶段**：清单出齐后再逐条判——**吸收**（修正论点 / 补边界）、**驳倒**（给出反驳理由）、或**确认破例并标明**，并记回 `claim.md` / `evidence.md`（潜在漏洞、待核查项）。

两阶段都在本步内完成，不引入额外的用户等待。

## 用户驳回某条反例时

防止模型被一劝就软掉立场：

- **算有效驳回**：给出决定性的一段材料、一个反例、一次逻辑订正。**一条就够**，不按凑了几条计分。
- **不算有效驳回**：「我觉得没问题」/「我不同意」但没给论证 /「这只是我的个人风格」/ **把挑战换个说法再自己回答一遍**（转移话题）/ 只说「你说得有道理」却不给具体修改。

**驳回要留痕**：只记用户真正驳回的那几条，写进 `evidence.md` 的「驳回台账」——挑战原文 / 用户的决定性回应 / 结论（**已处理** · **撤回**（评审者误判）· **收窄**（剩余问题在此））。

> **没有这一条，下一轮你会重复问同一个已被驳回的质疑。** 用户驳回的是你的误判时，不要暗示用户该改稿。

## 反例优先级

① 本地语料（你的 Obsidian 知识库与本地仓库）→ ② 你已发表的历史文章 → ③ 你的 GitHub 仓库 → ④ 联网（通用检索）。**先在自己的语料里找，再向外扩展**；不跑脚本。

## 改谁

若需改稿，改你自己的 `ai-draft.md`，并在「对你草稿的建议」里提示用户，**不直接改用户的草稿**。
